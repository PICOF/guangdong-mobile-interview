### Q02｜你怎么理解我们这个岗位？

我理解这个岗位要做的是：先弄清业务要解决什么问题，再把它变成能交付、能维护的软件。AI 可以参与写代码、做评审和补测试，但需求是否理解对、系统能不能安全上线，还是开发人员负责。

我看到招聘里还有一块是 Skill、MCP、脚手架和研发规范。这说明工作不只是完成自己的功能，还要把常用做法整理好，让其他同事也能稳定复用。例如统一接口格式、错误处理、权限校验和测试入口，减少每个项目从头摸索的时间。

所以我会同时准备两方面：一方面把一个功能从页面做到后端、测试和部署；另一方面解释怎么让 AI 参与其中，而且产生的修改可以检查、可以回退。

### Q03｜为什么选择广东移动？是觉得国企稳定、轻松吗？

稳定是我考虑工作的一个因素，但我主要看的是岗位内容和能长期积累的能力。这个岗位明确写了 AI 编码、Skill/MCP、全流程自研和系统稳定性，和我做 Agent、后端以及 AI 辅助开发的经历有直接联系。

移动的业务离真实用户和日常运营很近。一段程序能跑还不够，它还要接入已有系统、遵守数据权限、长期维护。我想在这种环境里把工程基本功做扎实，也把自己做过的 AI 应用从个人项目逐步推进到真实业务。

我不会把国企理解成没有交付压力。对于系统开发岗位，功能、故障处理和上线责任都需要有人承担。

## AI 编码、Skill、MCP 与研发规范

### Q16｜给你一个需求，你怎么用 AI 从头做到上线？

我会先把需求变成能检查的行为。比如做一个经营数据查询页面，要先明确谁能查、查什么指标、日期怎么算、没有数据或无权限时显示什么。把这些说清楚以后，再确定接口和数据结构。

接着拆成小任务，让 AI 先读相关代码和项目规则，再分别完成接口、页面、测试。我会要求它说明会改哪些地方，避免顺手改一大片。每完成一块，就看修改、跑对应验证，再做前后端联调。

准备发布时，还要确认配置、数据迁移、日志、健康检查和回退办法。上线后观察错误率、耗时和关键业务结果。对我来说，AI 负责加快一部分工作；“需求是否做对、风险是否可接受”要由人和实际验证来判断。

**追问：怎样证明需求清楚？**拿具体例子验收，例如无权限用户访问别的地区数据应被拒绝，不能只写“支持权限控制”六个字。

### Q17｜你实际怎么使用 AI 编程工具？

我使用过 Codex，并在项目里维护 Rules、MCP 配置和评测 Skill。我的思路是把项目约束和可调用能力整理出来，减少每次都重新解释同一套背景。

例如涉及数据查询时，不是让模型直接自由操作数据库，而是通过有约束的工具执行；涉及修改和评测时，让它沿着规定流程读代码、给出修改、运行检查、保留结果。我自己的重点是检查它有没有理解错需求、改错范围，以及测试结果能不能支撑结论。

如果问我 AI 写了百分之多少代码，我没有可靠统计，就不报一个好听的数字。更有意义的是我是否理解最终代码，是否能解释关键设计，以及工具不用时我能否继续排查问题。

### Q18｜Rules、Skill、MCP 有什么区别？别背定义。

我会用一个例子说明。假设我要让 AI 帮忙改接口：

- **Rules** 像项目的固定约定：接口怎样命名、哪些信息不能写进日志、修改后要检查什么。
- **Skill** 像一项工作的操作说明：做接口评审时先看权限，再看参数、错误处理和测试，必要时配套脚本、模板或资料。
- **MCP** 是接工具和上下文服务的一种协议：让 AI 应用用统一方式发现、调用工具或读取相关资源。

三者可以配合，但作用不同。说明里写“不能越权”只是要求；工具服务真正限制账号权限，才是执行上的约束。具体 Skill 的格式和触发方式要以所在平台为准，不是所有产品都完全一样。

### Q19｜让你给团队做一个 Skill，你会怎么写？

我会先选一个高频、范围明确的任务，比如“后端接口变更评审”。先写清什么时候用，需要哪些输入：需求说明、变更代码和接口契约。然后给出固定检查顺序：权限有没有扩大、参数有没有校验、返回值是否兼容、失败是否正确处理、哪些测试需要执行。

输出也要固定，至少说明发现的问题、对应位置、影响和验证证据。遇到缺少环境、测试失败或者需求不清楚，要明确停在哪一步，不能生成一句“全部通过”就结束。

我会拿历史变更和故意放入的问题做验证，看看它能否找出真实缺陷，会不会乱报。确认有价值后再逐步推广和维护版本。这是我会采取的团队建设方案，不等于我已经在公司推广过完整平台。

### Q20｜你会怎么设计一个 MCP 工具？

先从用途和权限边界开始。比如“查询允许访问的经营指标”，输入可以是指标名、时间范围和维度，输出要有结果、指标口径、数据时间和错误信息。当前用户是谁、能查哪些地区，应该来自服务端可信的登录信息，不能让模型自己填“我是管理员”。

执行前做参数和权限检查，执行中限制耗时和输出大小，执行后记录必要的审计信息。工具尽量只做一件清楚的事，别把“运行任何命令”作为万能接口。

我自己的企业 Agent 已封装 Schema、只读 SQL、知识检索和指标定义四类工具。多租户生产权限、企业级身份集成等如果要落地，还需要额外设计，不能把四个工具等同于完整企业权限平台。

### Q21｜MCP 和 Function Calling、普通 HTTP API 的区别是什么？

Function Calling 可以理解为模型提出“调用哪个工具、参数是什么”的结构化请求，真正执行仍由应用控制。MCP 解决的是 AI 应用怎样和工具、上下文服务对接。普通 HTTP API 则是服务对外提供能力的一种常见方式，它本身也可以被工具包装后使用。

所以不是三选一。例如底层已有一个 HTTP 查询接口，MCP 服务可以把它包装成标准工具，模型再通过工具调用请求使用它。业务鉴权和参数检查仍然要做，不会因为接了 MCP 就自动安全。

如果只是一个稳定的小应用调用一个内部函数，直接调用也可能更简单。我选择 MCP 的理由应该是多个工具或客户端之间确实需要统一接入，而不是为了增加一个技术名词。架构解释参考 S7。

### Q22｜AI 写出的代码，你怎么评审？

我先拿需求对照代码，看它有没有做错事情；然后看权限、数据库更新、异常处理和兼容性；最后才看命名、重复代码等可维护性问题。

例如点赞接口，不能只看“点击后数字加一”。还要看重复请求会不会多加、两个请求同时来会不会写错、数据库一半成功时能否回滚、失败时页面会不会显示成功。这些是实际业务要求，需要独立于 AI 的实现来检查。

AI 评审可以帮助我发现遗漏，但关键问题要回到代码路径和可复现案例。评审结果最好带位置、触发条件和后果。不能因为 AI 写了代码、又有另一个 AI 说没问题，就认为已经完成验证。

### Q23｜AI 自己写测试，自己跑通过了，为什么还不够？

因为代码和测试可能犯同一个错误。比如需求规定优惠券最多用一次，AI 却理解成每笔订单可用一次，它可能同时写出错误实现和验证错误行为的测试，两边一致但业务不对。

我会先从需求和已有规则准备独立验收样例，再看正常路径、边界和失败路径。必要时和旧系统、人工计算或可信结果对照，还可以有意破坏一个关键判断，检查测试是否真的会失败。

测试通过说明这些样例下没发现问题，不等于覆盖全部情况。覆盖率高也不代表断言有用；测试只调用了函数，却没有检查结果是否正确，价值很有限。

### Q24｜你怎么证明 AI 编码提高了效率？

我会比较同类任务的交付过程，不只数生成了多少行代码。至少看开发加评审总耗时、返工次数、缺陷、测试情况和模型使用成本。AI 很快生成代码，但后面花几小时修错，不能算整体提效。

比较时还要尽量控制任务难度、开发者经验和熟悉程度。可以先在范围较小的重复任务中试点，比如补接口测试、迁移规范化代码；复杂架构和高风险修改单独观察。

我目前没有经过严格对照的个人提效百分比，不会声称“效率提升80%”。我能说明哪些工作适合交给工具、我怎样检查它，以及我会怎么收集证据。

### Q25｜你会怎么给 AI 下一个比较好的编码指令？

我会交代五件事：要解决什么、相关代码在哪里、不能破坏什么、怎样判断完成、最后需要交付什么。例如：“给订单列表加分页，沿用现有登录鉴权和错误格式；每页最多50条；相同时间的订单也不能重复遗漏；补边界测试，并解释数据库查询和索引选择。”

这样 AI 才知道要守住哪些条件。一次只安排一个清楚的改动，让它先了解现有实现；如果任务需要改变接口或数据库结构，先把方案讲清楚再继续。

具体数值是这个假设场景的约束，不是你的已有项目参数。指令写得再详细，也要看实际结果，不能把“提示词很完整”当作完成证明。

### Q26｜代码库很大，AI 读不全怎么办？

我不会把整个仓库一次塞进去。先找需求对应的入口、调用链、接口定义和测试，把真正相关的文件给它；再补必要的项目规则。先弄清哪些模块拥有哪些数据和职责，比读一大堆无关文件更有用。

复杂任务可以拆成调查、设计、实现和验证几步，每一步保留明确结论。上下文中的事实应指向当前代码版本，不能依赖一份很久没更新的摘要。

如果 AI 开始引用不存在的函数，我会让它回到仓库核实，不继续让它靠记忆猜。把上下文缩小，是为了减少误解，不是让它忽略跨模块影响。

### Q27｜AI 总在同一个问题上修不好，你怎么办？

我会先停止让它盲目反复改。把失败现象整理成最小可复现案例，明确预期结果、实际结果、错误日志和最近改动。然后判断是需求理解错、代码逻辑错、环境问题，还是外部依赖失败。

例如数据库查询超时，就要看真实 SQL 和执行过程，不能只让它不断换提示词。必要时先回到已知可用版本，缩小差异，再逐个验证假设。

AI 可以帮忙列出可能原因和读日志，但每个猜测都要有检查办法。反复尝试次数也要有限，避免修一个问题又引入三个问题。

### Q28｜Rules 里写了禁止读敏感数据，能保证安全吗？

不能。Rules 能告诉 AI 应该怎样做，但不是数据库或操作系统的权限控制。模型理解错，或者受到外部文档里的恶意指令影响，都可能提出不合适的操作。

真正的限制应该放在执行工具和服务端，例如只给只读账号、限制表和数据范围、阻止访问未授权目录、对高风险动作增加审批和审计。即使模型提出越权请求，执行层也要拒绝。

我会把“行为规则”和“强制权限”分开设计，前者减少出错，后者限制出错后能造成的影响。是否安全还需要具体权限测试，不是装了某个框架就能保证。

### Q29｜公司代码、客户数据能直接发给外部模型吗？

不能默认可以。要先按公司的数据分类和工具使用规定，确认哪些代码、文档和数据允许进入什么环境。账号密钥、客户身份信息和完整生产数据不能为了方便直接贴进去。

需要排错时，优先提供去除敏感信息的最小样例、错误结构和必要代码；对不允许外发的内容，使用公司批准的内部能力。日志也要避免再次泄漏同样的信息。

这并不意味着所有开发都无法使用 AI，而是先把允许范围、工具权限和数据处理流程定清楚。具体部署选择由公司要求和业务条件决定，我不会假定“私有部署就没有任何风险”。

### Q30｜什么是适合 AI 编码的脚手架？你会放些什么？

我理解脚手架是新项目能直接开始开发的一套基础结构。对 AI 编码来说，尤其要减少“每次猜该怎么写”：目录职责清楚，接口和错误格式统一，配置从哪里来明确，测试与启动命令能直接运行。

我会放入一个最小但完整的功能示例，贯通页面、接口、权限、数据访问和测试；再提供日志、健康检查、容器配置、规则说明和常见任务模板。新功能照着这个路径扩展，AI 和新人都更容易理解。

但脚手架不应该把所有框架和中间件都装进去。先覆盖团队常见业务，再根据真实重复需求抽取公共能力；否则初始化很快，后面每个人都要删一堆东西。

### Q31｜哪些适合做公共组件？哪些不该抽？

多个业务都需要、行为比较稳定的东西适合复用，例如统一错误处理、身份校验接口、审计记录、配置加载、常见表格和表单。抽出来以后要有清楚的输入输出、版本和示例。

具体业务规则不要因为看起来相似就过早合并。例如两个活动都叫“优惠”，一个按客户等级、一个按套餐生效时间，强行做成一个超大通用函数，反而更难维护。

我会先看重复是不是真实存在，再决定抽象边界。公共组件升级也要考虑兼容性，不能我改了一个默认值，让所有业务一起出问题。

### Q32｜怎么让团队愿意用你做的 Skill 或工具？

先找大家确实觉得费时间、又比较重复的事，做一个小范围试点。比如接口联调前的契约检查，如果它能提前发现字段不一致，能省掉沟通和返工，大家就更容易接受。

我会提供最小示例、失败说明和反馈入口，同时看实际效果：有没有减少遗漏，会不会制造误报，使用成本是否太高。有效的部分再变成团队共同维护的规范。

推广不能只靠强制要求“每个人必须用”。如果工具比手工还麻烦，我要先改工具。这是我的推进思路，不把它说成已完成的跨部门落地成果。

### Q33｜AI 能自动提交代码、执行命令、发布生产吗？

技术上可以接这些能力，但我会按风险划分权限。读代码、生成候选修改和跑隔离测试可以更自动；修改生产数据、发布服务或变更权限需要更严格的身份、审批和回退机制。

执行命令也不能给无限范围。要限制目录、网络和凭据访问，必要时在隔离环境中运行，保留实际执行记录。AI 说“我只改了一个文件”，要用真实变更检查核实。

自动化程度应该随着验证能力提升，而不是工具一接上就放开所有动作。对小而明确、可恢复的工作可以逐步增加自动化，对高影响操作保留明确责任人。

### Q34｜你怎么看 TDD、先写规格再让 AI 实现？

我觉得价值是先把“什么叫做对”讲清楚。TDD 强调先写一个会失败的测试，再实现功能并整理代码；先写规格则会把业务规则、接口和验收条件先确定下来。两者可以配合。

AI 很擅长快速生成实现，因此更需要独立的目标。比如余额不能变负、同一请求不能重复扣费，这些约束先确定，才能检验生成代码是不是满足要求。

也不是每一行样式改动都要套完整流程。对交易、权限、复杂状态变化等高风险逻辑，我会更严格；对小范围可逆修改，验证要与影响相匹配。不要为流程本身增加很多形式化工作。

### Q35｜AI 已经能写代码了，为什么还需要你？

因为最难的部分经常不是把几行代码写出来，而是弄清该做什么、哪些条件不能破坏，以及出了问题由谁定位和修复。业务人员说“做个智能查询”，还需要有人确认指标口径、用户权限、失败处理和验收标准。

AI 能降低实现成本，但也会非常快地生成看起来合理的错误。开发人员要能看懂修改、理解系统影响、设计验证，并在信息不完整时做取舍。

所以我希望自己的价值不是“比 AI 打字快”，而是能把需求和工具组织好，对交付结果负责。我会用 AI，但不会把责任交给 AI。

## 企业分析 Agent、RAG 与研究项目

### Q36｜挑一个最相关的项目，详细介绍。

我想介绍企业经营分析 Agent。它针对的问题是：业务人员提出一个经营问题，往往既要查数据库里的数，又要查文档里的指标解释。只查一边，可能算出了数字却不知道是什么意思，或者解释正确但数字没依据。

项目在训练营团队原型之后由我做个人工程化重构。我用 LangGraph 组织查询流程：数据问题走数据库，知识问题走检索，需要两边信息就分别处理再汇总。数据库查询通过受控工具执行，结果里保留 SQL、引用、警告和调用记录。前端是 React/TypeScript，后端是 FastAPI。

我重点解决的是“结果怎么检查、权限怎么约束、失败怎么呈现”。目前我能说明的是本地工程实现和验证，不把它说成已经在大型企业生产环境服务了很多用户。

**再追问难点：**优先讲 SQL 语义与安全、数据和文档口径一致、检索失败定位，别同时展开十个技术点。

### Q37｜这是你独立做的吗？团队原型和你个人工作怎么分？

不是整个项目从零开始都由我完成。最开始是训练营团队原型，已经探索过企业查询和 Text-to-SQL。后续我个人重构，重点做工作流组织、MCP 工具边界、检索适配和版本管理，以及前后端工作台和验证机制。

我会按模块和对应版本说明自己的工作，不把团队最初的想法、其他成员的代码都算成我的成果。如果需要，我可以顺着一个模块解释输入输出、关键判断和失败处理。

代码占比我没有按提交做严格核算，所以不说“90%都是我写的”。这个项目里，比比例更值得说明的是我实际改变了哪些行为、为什么这样改，以及我能否独立解释实现。

### Q38｜一个问题进来以后，系统到底怎么走？每个模块输入输出是什么？

拿“本月收入比上月下降多少，相关指标怎么算”作例子，这只是演示提问，不声称我已接入移动真实收入数据。请求先进后端，带着问题和必要会话信息；路由模块输出需要走的数据路径、知识路径和查询计划。

数据路径拿到表结构与指标说明，形成 SQL，通过检查后执行，返回数值、列信息和执行状态。知识路径把问题转成检索请求，返回相关片段、来源和检索状态。汇总与检查部分把两边结果合起来，确认数字、解释和引用是否对应。

最后前端收到答案、SQL、引用和异常提示。任一关键环节失败，就说明缺的是哪部分，不把“没有查到”写成“结果是零”。如果要生产落地，身份和数据权限还要在整个调用链持续生效。

**练法：**用手画“页面→接口→路由→数据/知识→检查→页面”，每个箭头说一句传了什么。同酒店面经 S2 明确提过输入输出追问。

### Q39｜为什么用 LangGraph？普通函数不能写吗？

普通函数当然可以写。我的流程里有分支、并行汇合、状态和失败处理，用图把步骤关系显式表达出来，比较容易看到请求走到了哪里，某一步失败以后应该怎么处理。

例如混合问题需要数据查询和知识检索两路，汇总前要知道两路分别有没有成功；失败修复也要控制次数，不能一直循环。我使用 LangGraph 主要是为了组织这些执行关系。

它不会自动让模型答对，也不会自动给数据库加权限。框架支持的持久化、人工介入等能力，也不能直接说我每项都实现了。如果只是一次检索加一次生成，普通函数可能更简单。框架定位参考官方资料 S8。

### Q40｜路由判断错了怎么办？为什么不是全部交给大模型？

不同问题需要的工具不同。一个指标定义问题没必要跑数据库；一个精确数值问题也不能只靠文档回答。我会结合明确规则和模型判断来分流，并在实际执行前继续做校验。

路由有不确定性时，应该澄清用户需求或采取保守路径。例如“看看收入怎么样”缺少时间和范围，直接生成查询很容易猜错。安全拒绝也不能完全依赖模型有没有识别出来，执行层还要独立限制权限。

路由效果要单独评估，收集哪些问题被分错、错误会影响什么，再调整规则或提示。简历提到五类路由，但现有材料只明确列出数据、知识、混合、安全拒绝等；第五类的准确名称要看实际代码，别现场凭空补一个。

### Q41｜Text-to-SQL 是怎么做的？能执行就说明正确吗？

Text-to-SQL 就是把自然语言需求转成数据库查询。我会先让系统知道表结构、可用字段、表之间的关系和指标定义，再形成查询计划和 SQL。执行前还要经过语法和权限检查。

能执行只说明数据库接受这条语句，不说明业务意思正确。比如用户问“收入”，模型可能选了订单金额，却没扣退款；或者把付款时间写成下单时间，SQL 一样可以跑通。

所以要用已知答案验证语义，包括时间范围、去重、退款、关联条件和空值处理。业务定义不清楚时，应先澄清，不由模型自行决定一个看起来合理的口径。

### Q42｜你怎样防止模型乱查、删库？为什么只读还不够？

我用了几层限制：SQLGlot 把 SQL 解析成结构后检查，限制可访问的表；数据库连接只读；结果最多返回500行；查询执行有15秒预算。这样即使模型生成不合适的语句，也不能直接照单执行。

这些限制解决的风险不一样。只读能减少写入风险，但仍可能读到不该看的客户资料。表白名单允许查询某张表，也不代表所有用户都能看表里的所有行和列。生产场景还需要把用户身份、地区、租户等权限落实到数据访问层。

此外，`LIMIT 500`只限制返回量。查询前面仍可能扫描或关联大量数据，所以还需要执行预算和资源限制。不能说“有 LIMIT 就不会拖慢数据库”。

### Q43｜SQL 失败如何重试？15秒到了是不是所有工作都停了？

我的设计是失败后只进行一次受控修复，修复后的 SQL 仍然要经过原来的检查。不能因为第一次失败，就让模型放宽表范围、取消预算，或者换成更危险的操作。

失败要分类：语法或字段问题可以尝试修复；越权就应拒绝；资源或环境故障不能靠不停改 SQL 解决。超过预算以后，应该明确告诉用户这次没有取得完整结果。

超时也要看实际实现。当前项目记录涉及 SQLite 的 progress handler 预算，不能泛化为所有外部服务都已被严格终止。调用方停止等待，不一定意味着下游数据库或任务已经停止；生产环境需要检查取消能否真正传递，以及资源是否释放。

### Q44｜有 Verifier，是不是就不会出现幻觉？

不是。Verifier 的作用是多一道检查，例如回答中的数字是否对应查询结果，引用是否存在，关键证据是否缺失，数据和解释有没有冲突。能用确定规则检查的部分，优先用规则，不必都让另一个模型判断。

如果检查器本身也是模型，它也可能犯错，甚至和生成模型犯同样的错。所以我不会把“通过 Verifier”当成百分之百正确，只把它当作一部分证据。

发现冲突或证据不足时，应该返回不确定性、重查或要求澄清。尤其是经营和财务数据，回答得流畅不能替代真实查询结果。

### Q45｜用大白话解释 RAG，它和微调有什么区别？

RAG 可以理解为“先查资料，再根据查到的资料回答”。文档先被拆成片段、建立索引；用户提问时先找相关片段，再把这些材料和问题一起交给模型，并返回来源。

微调则是利用训练样本改变模型参数，更适合改变特定任务的表现或输出习惯。公司制度今天更新，通常更方便更新知识库，不必每次重新训练模型；但这不意味着 RAG 能解决所有问题。

RAG 可能查错、漏查，也可能模型拿着正确资料仍然解释错。微调也不保证精确记住所有知识，两者可以结合。要先看问题属于知识更新、检索质量，还是模型行为与能力，再选方案。

### Q46｜文档怎么切块？切得越小越好吗？

不是。块太小会丢掉上下文，比如只保留“不得超过30天”，却不知道什么业务不能超过30天；块太大则可能混入很多无关内容，让检索和后续回答都变差。

我会优先按标题、段落和业务结构切，保留文档名、章节、版本和必要重叠。表格要特别注意表头、单位、条件和行的对应关系，不要把数值和含义拆开。

块大小没有一个对所有资料都最优的固定值。用真实问题检索，检查答案需要的证据能否完整取到，再比较不同切法。简历没有给出你最终的精确块长，面试别临时报一个固定数字当作项目参数。

### Q47｜BGE、BM25 各干什么？混合检索一定更好？

BGE 在这里用来把文本转成向量，便于按语义相似程度检索；BM25 更偏关键词匹配。用户换一种说法，向量检索可能更容易找对；如果问具体产品编号、错误码或者缩写，关键词匹配往往很有价值。

混合检索是利用两类结果的互补性，但需要考虑怎样合并排名、去重和控制噪声。两边分数的含义不同，不能随便直接相加就认为有意义。

我的研究项目分别接入过稠密和稀疏检索做对照。是否使用某个融合算法、重排模型和权重，要按实际实现说；不能因为知道混合检索，就声称项目已经完整上线了这套方案。

### Q48｜为什么主用 Milvus、后备用 FAISS？有什么代价？

FAISS 更像向量检索算法库，适合在程序内或本地构建索引；Milvus 提供更完整的向量数据服务能力，涉及持久化、元数据管理、过滤和服务化等。我的企业 Agent 用 BGE＋Milvus 作为主路径，FAISS 作为显式后备。

后备的意义是主路径不可用时仍然有一个受控选项，但切换不能偷偷发生。应该标明使用了后备、索引版本和可能差异，还要确保权限过滤和数据更新规则没有丢掉。

代价是多维护一条路径，需要验证同一语料下的召回和耗时。不能说 Milvus 必然比 FAISS 快，因为实际表现还取决于索引、参数、数据和部署环境。

### Q49｜知识库更新怎么做？别名切换、稳定 ID、内容哈希分别干什么？

稳定片段 ID 用来识别“这是哪个文档的哪一段”，内容哈希用来判断内容是否变化，幂等 upsert 则避免同一份内容重复导入产生很多重复记录。删除的文档也要处理，不能只追加不清理。

版本 Collection 可以把新旧索引分开。新版本先构建和验证，检查检索结果、数据量和权限过滤，再把查询别名切到新版本。出现问题可以切回保留的旧版本。

这套设计不是说切一个别名就解决了所有一致性问题。还要考虑向量模型版本、字段格式、正在执行的请求和缓存。新旧索引不兼容时，调用方配置也必须配套。

### Q50｜Recall@K、MRR、p95 是什么？怎样证明检索真的变好了？

Recall@K 看的是：已标注为相关的资料里，前 K 个检索结果找回了多少。比如某问题有两段必要证据，前五条只找到一段，召回率就是一半。前提是你有相对可信的相关性标注。

MRR 看第一条相关结果排得靠不靠前；排第一得1，排第二得1/2，再对问题求平均。p95 耗时可以理解为约95%的样本不超过这个时间，它能帮助发现“多数很快、少数很慢”的问题。

比较方案时，我会固定语料、模型、查询集、Top-K 和过滤规则，并保留没参与调参的问题。还要看最终答案的证据与正确性，因为“检索到”不等于“答对”。现有简历没有一组可核验的召回提升百分比，不补造数字。

### Q51｜RAG 答错了，你怎么查？

我会沿着链路逐段查。首先确认原始文档里到底有没有答案，版本是否正确；接着看切块有没有把必要上下文拆散；再看正确片段有没有进入候选结果，是不是被过滤或排序挤掉。

如果资料已经正确交给模型，回答还是错，就看提示、引用和生成过程。这样能区分“资料不存在”“资料没检索到”和“模型没用好资料”，不会所有问题都靠换更大的模型解决。

临时处理也要明确：证据不足就说没有足够依据，不能拼出一个看似完整的答案。修复后把这个失败案例加入回归集，避免下次优化别的地方时又退回去。

### Q52｜会话记忆是不是把聊天记录全存下来？

不应该简单地全部保存、全部塞回模型。要区分当前任务状态、短期对话和确实需要长期保留的信息。当前用户选了哪个时间范围，和用户很久以前提过的偏好，使用方式不一样。

记忆还需要来源、时间和更新规则。旧信息被用户纠正后应该更新；不同用户的记忆不能串；模型自己猜测的东西也不能直接沉淀为事实。保留多少、保存多久要符合业务和隐私要求。

我会根据任务检索相关记忆，而不是无限增长上下文。简历支持我做过会话记忆相关实践，但具体存储结构、跨会话范围和删除机制，需要按实际代码回答，不能把理想设计全部说成已完成。

### Q53｜DeepResearch/CoSight 项目，你原创了什么？

这些框架和基础模型不是我原创的。我的工作是独立部署、读执行链、做代码接入和实验，观察复杂任务怎样拆分、调用工具、检索、使用记忆，最后形成回答。

我接入过 BGE＋FAISS 和 BM25 两类检索，统一返回格式，并基于 Qwen3 对提示、任务拆分、检索和记忆策略做对照，保留检索失败、证据不足、答案冲突等样例。

我认为有价值的是能定位问题发生在哪一步，以及比较变化是否有效。比如最终结论错，不一定是最后一次生成的问题，也可能早期子任务方向偏了，后面一直在继承错误。这个项目不能包装成我发明了新的多 Agent 框架。

### Q54｜什么叫消融实验？多 Agent 为什么不一定更好？

消融可以理解为“其他条件尽量不变，去掉一个部件，看看影响”。比如固定问题和模型，去掉记忆，再比较任务完成情况，就能观察记忆在这组实验里有没有帮助。如果同时换模型、改提示又加检索，就很难说收益来自哪一步。

多 Agent 能让不同子任务分工，但也会增加调用成本、延迟、上下文传递和结果冲突。拆错任务之后，多个 Agent 可能只是更快地把错误传播出去。

我会先比较单流程能否满足目标。只有任务确实可拆、各部分输入输出明确，而且评测证明收益值得成本时，才增加协作复杂度；不会以 Agent 数量当作项目先进程度。

### Q55｜你到底用的什么模型？简历里那个模型 ID 是官方型号吗？

研究实验里我使用过 Qwen3。企业 Agent 的调用层做成了可配置的 OpenAI 兼容客户端，简历记录的 `deepseek-v4-flash` 是当时训练平台返回的模型 ID。

我会把“平台显示什么”与“实际底层模型是什么”分开说。如果没有服务方可靠信息，就不能仅凭字符串断言它是某个官方型号、参数规模或具备某种能力。

模型选择我更看任务结果、响应时间、成本、上下文和工具调用表现；在同一组问题上比较，避免只看宣传。封装统一调用层可以降低替换成本，但不同服务的参数、错误和工具调用行为仍然需要适配与测试。

## 前后端、微服务、数据库、测试与上线

### Q56｜前端点一下按钮，到看到结果，中间发生什么？

前端先检查必填项，把参数按接口约定发给后端，同时显示加载状态。后端完成身份鉴别、权限和参数校验，再调用业务逻辑、数据库或外部工具，返回约定的数据或错误。

前端收到结果后更新页面；如果超时或失败，给出明确提示和重试方式，不能一直转圈或者把旧数据当作新结果。用户连续发起两个查询时，还要防止慢的旧请求覆盖新的结果。

前端禁用按钮只能改善体验，真正防重复和权限检查仍然要在后端做。用户可以绕过页面直接调用接口，不能把页面隐藏某个按钮当作安全措施。

### Q57｜React 里你怎么管理状态？异步请求有什么坑？

我会把只影响当前组件的状态放在组件附近，比如输入框和展开状态；跨多个页面共享的登录信息，再考虑统一管理。服务器查询结果与本地编辑状态要区分，否则容易互相覆盖。

异步请求常见问题是顺序不同。例如先查A、再查B，A最后才返回，如果直接写状态，页面可能显示A的数据。我会用取消、请求标识或状态检查，确保只接收当前有效结果。组件卸载后也要处理对应资源。

列表需要稳定 key，副作用依赖要写准确，别在渲染过程中随意发请求。性能优化先看测量结果，不是所有地方都加缓存或记忆化。

### Q58｜FastAPI 的 async 是什么？写了 async 就能提高并发吗？

async 适合等待网络、数据库等 I/O 时让出执行机会，让同一执行线程可以处理其他等待中的任务。但函数里如果直接跑耗时的同步计算或阻塞调用，写了 async 也不会自动让它不阻塞。

例如大段 CPU 计算，需要考虑独立工作进程或任务系统；同步库调用要用适合的执行方式，不能随便堵住事件循环。数据库连接池、外部模型限流也会成为并发瓶颈。

所以我会测实际调用链：时间花在等待、计算还是数据库，而不是看到框架支持异步就宣称系统吞吐一定高。

### Q59｜怎么设计一个好用的接口？

先把请求和响应说清楚：哪些参数必填、类型和范围是什么，成功返回什么，失败怎样区分。接口还要有明确权限、分页上限和兼容规则，不能只给前端一个“随便传 JSON”。

例如查询接口，结果为空与查询失败要有区别；修改接口，参数错误、无权限和状态冲突也不该全部返回同一个“操作失败”。错误信息要帮助排查，但不能把数据库密码或内部堆栈直接暴露出去。

前后端可以先按契约并行开发，再用真实请求做联调。上线已有接口时，要考虑旧客户端还能不能用，新增字段和删除字段的风险不同。

### Q60｜短视频项目为什么拆成微服务？七个服务真的有必要吗？

项目按用户、Feed、发布、点赞、评论、关系和消息拆了七个 Kitex 服务，Hertz 负责 HTTP 网关。这样能练习清楚的服务边界、RPC 契约和服务发现，也方便理解不同业务模块怎样协作。

但我不会说所有项目都应该这样拆。服务一多，就有部署、网络调用、链路排查和数据一致性成本。小团队、小业务量时，模块化单体往往更容易交付和维护。

如果让我重新为一个真实业务选方案，我会先看团队规模、模块是否需要独立发布、性能瓶颈和业务边界，再决定是否拆分。训练项目的学习目标不能直接当成生产架构的充分理由。

### Q61｜Hertz、Kitex、Thrift、etcd 分别起什么作用？

Hertz 在我的项目里接收外部 HTTP 请求，做网关入口；Kitex 用于服务之间的 RPC 调用；Thrift IDL 约定接口方法、参数和返回结构，减少调用双方理解不一致；etcd 用于服务注册和发现，让调用方找到可用的服务实例。

例如请求点赞，先到网关，再通过相应 RPC 调用点赞服务。网关不应该在代码里固定某一台机器地址，而是通过注册发现获取实例信息。

服务发现不代表调用永远成功。实例可能刚下线，网络也可能超时，所以仍要处理超时、连接失败和受控重试。只有幂等或有重复保护的操作，才适合直接自动重试。

### Q62｜两个人同时点赞，计数会不会错？重复点赞怎么处理？

我会把点赞关系和计数更新放在同一个事务里处理，同时给“用户—视频”关系设置唯一约束，避免同一用户对同一视频重复插入。计数要用数据库里的原子更新，不能先读一个数到应用里，再各自加一覆盖回去。

如果关系插入失败，不能继续把计数加上；取消点赞也要确认确实删掉了对应关系，再减计数。事务失败要整体回滚。唯一约束是数据库最后一层保护，不能只在业务代码里先查有没有。

我的简历还提到关注变更中引入行锁；不要把它扩张成所有接口都用了同一套锁。将来如果关系和计数跨数据库或服务，就不能再假设一个本地事务能够包住全部更新，需要另行处理一致性。

### Q63｜事务是什么？隔离级别解决什么问题？

事务是把一组相关更新作为一个整体处理。例如点赞关系写成功、计数更新失败，不能长期只完成一半。事务要么按规则提交，要么失败回滚，但它的范围通常是当前数据库事务，并不会自动覆盖所有外部服务。

隔离级别决定并发事务之间能看到什么，会影响脏读、重复读到不同结果等现象。隔离越严格，往往并发代价也越大；具体表现还取决于数据库和访问方式。

在 MySQL InnoDB 里，普通快照读和 `FOR UPDATE` 这类锁定读行为不同。不能背一句“可重复读”就认为每个读写组合都自动正确，要结合唯一约束、原子更新和必要的锁来保证业务不变量。

### Q64｜SQL 慢了怎么办？索引是不是越多越好？

先拿到真正慢的 SQL、参数和数据规模，再看执行计划、扫描行数、连接顺序、排序和锁等待。不能只看到接口慢，就确定是缺索引；连接池等待、网络和数据库负载也可能有影响。

索引要围绕查询条件和排序设计，联合索引尤其要看字段顺序和实际访问方式。对于重复出现的大范围统计，预聚合可能比不断加索引更合适，但要承担更新和一致性成本。

索引不是越多越好，它占空间，也增加写入维护成本。优化前后要在接近实际的数据上比较，并确认结果没变。我的 Agent 有超时案例，但没有证据的优化收益不能说成已经实现。

### Q65｜Feed 为什么用游标分页？同一时间的视频怎么办？

项目 Feed 按发布时间倒序拉取，每次限制30条。和大偏移量分页相比，游标方式能避免越翻越深时反复跳过大量旧数据，也更适合持续产生新内容的列表。

如果只用时间当游标，同一时刻有多条记录时可能重复或漏掉。更稳妥的设计是用“时间＋唯一 ID”作为排序和游标边界，保证顺序确定，查询条件也要与排序完全一致。

这里要分清已有实现和改进建议：简历明确的是时间游标和30条限制；是否已经实现复合游标，需要核对仓库，不能把建议说成我已经完成的特性。

### Q66｜JWT、bcrypt 是什么？有 JWT 就安全了吗？

JWT 在这里用于承载并验证登录相关信息，服务端要检查签名、有效期等条件。普通签名 JWT 的内容通常可被解码查看，不能把密码等秘密放进去。知道用户是谁之后，还要判断他有没有权限操作这个资源。

bcrypt 用于保存口令的哈希，不是保存可还原的明文密码。它通过盐和可配置计算成本增加口令猜测代价，登录时用相应算法验证。

有 JWT 不等于安全。令牌泄漏、过期控制、登出失效、签名配置和对象权限都要考虑；前端存储方式还要结合 XSS、CSRF 等风险。不能只校验“令牌合法”，就允许查看任意用户数据。

### Q67｜视频上传怎么做？MD5、MinIO、FFmpeg 分别有什么用？

项目上传链路用 MD5 生成对象名，FFmpeg 抽帧生成视频封面，MinIO 存对象，通过 Nginx 提供访问入口。我配置过四节点、八数据卷的 MinIO 环境。

MD5 在这里是内容命名或识别的手段，不能当作防恶意碰撞的安全保证。生产上传还要检查大小、类型、访问权限和处理资源限制，不能把任意文件都直接交给工具处理。

还要考虑部分失败：对象已经上传，数据库记录没写成功，怎样清理；转码失败，前端显示什么。多个容器如果都在一台宿主机上，也不能说具备跨机器故障容灾能力。

### Q68｜Trace、日志、指标有什么区别？你怎么定位一个慢请求？

日志记录具体事件，例如哪次查询失败；指标适合看整体趋势，例如错误率和请求耗时；Trace 把一次请求经过的多个步骤串起来，帮助看到时间花在哪个环节。

我的微服务项目在网关和 Kitex 调用两侧接入过 OpenTelemetry，配合 Collector、Jaeger 和指标展示组件。定位慢请求时，我会先看哪些请求变慢，再顺着 Trace 找是网关、RPC、数据库还是外部依赖耗时。

关键是传播同一次请求的追踪上下文，不是每个服务各自生成互不相关的 ID。记录时也要控制敏感字段，保留排查需要的信息即可，不把完整客户数据全塞进日志。

### Q69｜什么时候加 Redis？缓存穿透、击穿、雪崩是什么意思？

先确认瓶颈是不是重复读取同一类数据，再考虑缓存。缓存适合读多写少、能接受一定更新延迟的数据，但会带来过期和数据库一致性问题。简历没有证明我在这个短视频项目中实际用了 Redis，所以这里讲的是设计知识。

穿透是反复查询不存在的数据，缓存和数据库都查不到；击穿是一个很热的键失效，大量请求同时压到数据库；雪崩是大量缓存同时失效或整个缓存服务故障。可分别考虑参数校验与短期空值缓存、请求合并、错开过期与限流降级等。

方案也有代价，例如布隆过滤器有误判，逻辑过期会返回旧值。要结合业务能不能接受陈旧数据来选，不能把缓存当成万能提速开关。

### Q70｜什么是幂等？超时以后重试为什么可能危险？

幂等是同一个操作重复执行，最终业务效果和执行一次一致。例如“把状态设为已读”通常容易做到；“余额减100元”重复执行就会多扣。

请求超时，只能说明调用方没在规定时间拿到结果，不能证明服务端没执行成功。因此扣费、创建订单这类动作需要业务唯一键或幂等键，在服务端原子地检查和记录，重复请求返回原有结果或明确状态。

幂等键要和用户、动作及必要参数绑定，不能不同请求碰巧用了相同键就混用结果。失败恢复也要考虑处理中状态，不能把所有重复请求简单当作已经成功。

### Q71｜Docker Compose 能启动了，为什么不代表可以生产上线？

Compose 能帮助我把服务和依赖在可控环境里拉起来，方便复现。但生产上线还涉及数据持久化、备份、访问控制、密钥管理、资源限制、监控告警、故障恢复和发布流程。

例如数据库容器删了数据是否还在，依赖还没就绪时应用会怎样，日志是否持续占满磁盘，版本升级失败能否回退，这些都要验证。配置还要区分开发和生产，不能把测试密码直接带上去。

我会准确说明自己做过的是开发和验证环境编排。面向生产的增强，我能解释设计，但不把“本地启动成功”说成“已经具备生产级高可用”。

### Q72｜如何发布新版本？回滚有什么容易忽略的地方？

发布前先固定代码和配置版本，完成相应测试，说明变化范围、监控项和回退条件。上线时可以根据系统条件逐步放量，观察错误率、耗时和关键业务结果，再决定继续还是停止。

回滚不仅是换回旧镜像。新版本如果改了数据库结构、消息格式或索引，旧程序可能已经读不懂。比较稳妥的是先做兼容性扩展，让新旧版本有过渡期，再在确认不用旧结构后清理。

重要数据变更还要考虑备份和恢复演练。不能把“我们有旧代码”当作完整回滚方案，也不能因为新版本启动正常就忽略业务结果是否变化。

### Q73｜上线后突然大量报错，你会先做什么？

我会先确认影响范围和严重程度：哪些功能、多少用户、有没有数据错误，是否刚发布或依赖刚变化。先止住继续扩大的影响，例如暂停放量、关闭出问题的非关键功能，必要时按预案回退，并及时同步相关负责人。

同时保留日志、Trace 和时间线，判断是配置、依赖、资源还是代码问题。故障期间不凭感觉同时改很多东西，否则既可能扩大影响，也很难确认根因。

恢复后确认关键流程和数据状态，再复盘触发原因、为什么没提前发现、怎样补监控和测试。这是我的处理思路，不编造一段“我独立处理过大规模线上事故”的经历。

### Q74｜一个功能应该怎样测试？单元、集成和端到端有什么区别？

单元测试验证较小的逻辑，例如金额计算或参数检查；集成测试验证模块与真实依赖协作，例如事务是否回滚、RPC 契约是否一致；端到端测试从用户操作走完整流程，看页面、后端和数据是否连得上。

我会按风险分配，而不是所有情况都用最慢的端到端测试。规则复杂的地方多做单元测试，数据库和权限边界需要真实集成验证，最关键的用户流程保留端到端检查。

正常路径之外，还要覆盖无权限、空数据、重复请求、并发、依赖失败和超时。测试要检查结果和副作用，而不只是返回状态码成功。简历里22个测试函数是数量，不能据此推导覆盖率和充分性。

### Q75｜你实习写 TPS 2000、响应不超过1.5秒，这说明系统很强吗？

这只能说明团队测试环境中相应负载条件下的结果，不能直接证明任何环境、任何接口都能达到。解释时需要补测试接口组合、数据规模、机器配置、持续时间、并发和错误率，以及“1.5秒”到底是平均、最大还是某个分位数。

我在项目中参与接口开发、联调、测试与问题定位，但不能把团队整体性能归功于我个人某一次优化。现有材料没有完整记录统计口径，因此我会说明已知边界，精确结论需要回看报告。

TPS 和并发数也不是一回事：前者是每秒完成多少事务，后者是同一时刻有多少工作在处理中。把并发设置成2000，不等于实际吞吐达到2000 TPS。

### Q76｜Go 协程和线程有什么区别？怎么避免协程泄漏？

goroutine 是 Go 运行时调度的并发执行单元，运行时把很多 goroutine 调度到操作系统线程上。创建成本通常较低，但不是零成本，开很多协程也会占内存、连接和其他资源。

泄漏常见于一直等不到消息的 channel、没有退出条件的循环、外部调用不返回。设计时要明确谁启动、谁取消、谁回收，用 context 传播取消和超时，控制并发数量，并保证阻塞操作有退出路径。

channel 不是加上就线程安全，多个协程共享 map 仍可能发生竞争。可以通过所有权设计、锁或其他同步机制保护，并用竞态检查帮助发现问题，但也不能认为检测没报错就覆盖了全部执行时序。

### Q77｜你做过 Java 后端，Spring Boot、Spring MVC、事务怎么理解？

Spring MVC 主要负责 Web 请求处理：请求进入控制层，参数被解析和校验，再调用业务服务，最后返回结果。Spring Boot 通过自动配置和约定减少搭建应用的重复工作，它不是另一个与 MVC 完全对立的东西。

业务逻辑不要全堆在 Controller，数据访问和事务边界要清楚。事务通常放在需要保证一组更新整体成功的服务逻辑处；也要理解框架代理的适用范围，不能以为方法上写个注解就一定在任何调用方式下生效。

我在向心力做过 Java 后端和接口联调，但如果被问到没实际用过的框架细节，我会说明理解和实践的边界，不用“参与项目”冒充“精通所有组件”。S5 有 MVC、多线程等历史追问题型。

### Q78｜浏览器访问一个页面，大致经历什么？HTTPS 多了什么？

浏览器先根据域名找到服务器地址，建立传输连接，再发 HTTP 请求，服务器返回页面或数据，浏览器解析并展示。实际过程中会受到 DNS、连接复用、缓存、代理和所用 HTTP 版本影响，不能机械地说每次访问都从头建立所有连接。

HTTPS 在 HTTP 的通信外加入 TLS，主要提供加密传输、完整性保护和服务器身份验证，帮助防止中途窃听与篡改。它不能自动防止后端越权、SQL 注入或业务逻辑漏洞。

排查访问慢时，也可以沿这条路径拆：域名解析、建连、TLS、服务器处理、资源下载和页面渲染。不要所有慢都归因于带宽。

## 光储项目、实习、指标与个人贡献

### Q79｜你的光储项目到底做了什么？跟系统开发有什么关系？

可以把园区理解成一个有光伏、用电负荷和储能电池的系统。我的问题是：什么时候充电、什么时候放电，才能在满足设备和供电约束的前提下，让综合成本更低。

我整理了60,013个五分钟时段的数据，包括负荷、五路逆变器光伏、分时电价和电池状态，再搭建离线回放，按当时能得到的信息做预测和调度。主要方案是滚动 LP-MPC，也评估了安全强化学习候选方案。

与系统开发相关的部分，是数据处理、模块输入输出、约束检查、实验复现和失败回退。算法给出一个动作只是其中一步，还要判断它是否可执行、结果如何记录、怎样验证。现在的结果是离线验证，不是我已经控制了真实电池运行。

### Q80｜LP-MPC 是什么？为什么看未来24小时，却只执行第一步？

可以理解成“往后做一份计划，但先走眼前这一步”。我把未来24小时分成288个五分钟时段，结合预测、电价和电池状态，算一份满足约束的充放电计划。LP 表示这个优化问题采用线性规划形式，MPC 表示持续滚动地重新规划。

只执行第一步，是因为未来预测会变，设备状态也会变。五分钟之后拿到新的信息，再重新算，比死守昨天算好的整天计划更灵活。

约束包括 SOC 10%—90%、功率平衡和禁止逆送等。终端状态条件可以避免把电池在预测窗口末尾过度消耗，从而让短期成本看起来低。具体终端公式要按实现解释，不能自己加上未核实的成本项。

### Q81｜简历写“因果预测”，是在做因果推断吗？怎样避免偷看未来？

这里最重要的含义是时间上的因果约束：在某个时刻做决定，只能用当时已经知道的信息。比如用历史已实现误差选择预测方法，不能先看完整天实际数据，再挑当天表现最好的方法回填过去。

这和识别某个变量对另一个变量的因果效应，不是同一件事。我不会只凭这个项目标题就声称做了完整的因果推断研究。

避免未来信息泄漏，要检查数据切分、缺失值处理、特征计算和标准化等环节。例如对某个时刻的缺失值，用未来观测插值后再拿去模拟在线决策，就可能引入偷看未来。评估要遵循真正部署时可获得的信息范围。

### Q82｜6.85%到底怎么算？为什么不能说给公司省了五万元？

在固定的综合成本口径下，基准约74.19万元，LP-MPC约69.11万元。用两者差值除以基准，得到约6.85%，差额约5.08万元。展示的金额已四舍五入，精确比例以原始报告为准。

这是基于真实测量数据进行的离线反事实回放，意思是在同样数据和既定假设下比较“如果用不同策略会怎样”。它不等于真实设备已经按该方案运行，也不等于公司账单真的少了5.08万元。

要进一步解释，还需要说清基准策略名称、成本组成、数据区间和约束是否一致。现有简历没有给全这些细节，我不会自行补出一个电价、设备容量或成本公式。面试前能找到原报告就核对；找不到时保留边界，不硬讲不记得的细节。

### Q83｜为什么还做强化学习？它比 LP-MPC 好吗？

我做强化学习是想探索另一类决策方式，不预设它一定更好。项目包括带物理安全层的 Double DQN，以及在 LP-MPC 动作附近做有界调整的 Residual RL。

候选动作要先满足物理约束，再看经济表现。现有项目准备材料记录：安全 Double DQN 推理较快，但综合成本没有优于 LP-MPC；因此不能只挑速度这个指标宣布强化学习获胜。未达到要求的候选会回退到 LP-MPC。

如果被问根因，我只能说需要继续检验奖励与最终成本是否一致、训练覆盖、预测误差和随机性，不能没有对照实验就断言某一项是原因。尝试过并验证不适合当前条件，也是一项有效结论。

### Q84｜你在华为海思做的 RDMA 是什么？具体负责哪段？

RDMA 是远程直接内存访问。在合适的硬件和软件支持下，可以让网络数据传输减少传统处理路径中的一些 CPU 参与和内存拷贝开销，常用于对吞吐和延迟要求较高的场景。

我实习时面向存储介质间的高速可靠传输，参与的是相关软件方案中的网络消息编解码、分包和传输逻辑，也在框架模拟硬件环境下编写测试。

我的职责边界是这些软件环节，不是独立设计整套 RDMA 协议或网卡硬件。如果追问，可以解释消息格式、边界长度、分包与重组怎样验证；涉及未提供或不便公开的内部字段，不应该为了显得详细随意编造。

### Q85｜“功能引入后性能影响低于1%”怎么测？是不是你提速了1%？

不是提速1%。这句话表达的是在当时的测试范围内，引入功能前后整体性能变化较小。它需要同环境、同负载比较，也需要明确测的是吞吐、延迟还是其他指标。

我能确定自己在框架模拟硬件环境里做了编解码和分包相关测试。现有材料没有记录全部硬件、样本数和统计波动，所以不能把“低于1%”扩张为所有场景下的严格保证，更不能说成生产大规模收益。

如果需要重新验证，我会固定输入和环境，多次测量，区分正常波动与稳定差异，记录原始数据。数字很小的时候，尤其要关注测量误差。

### Q86｜向心力的取证系统做什么？区块链存证保证内容真实吗？

我在向心力 Centfor 参与过云业务取证系统后端，做多平台信息调用、客户信息管理和业务数据库相关工作，也参与接口联调和测试，系统涉及服务数据及区块链存证信息管理。

存证可以帮助证明某份记录在特定条件下存在、后续有没有被改动，但不能自动证明采集进来的内容本身就是真的。原始数据来源、采集流程、身份权限和时间记录仍然重要。

具体链平台、智能合约、共识算法和法律证据效力，现有材料没有提供我独立负责的证据，不会把它说成我从零做了整套区块链。实习单位按最新确认是向心力，不沿用旧表单里的“中国联通”误填。

### Q87｜哪件事最能体现你的主动性？

我会选企业 Agent 的个人重构。团队原型已经能探索自然语言查询，但我希望进一步解决“别人怎么判断结果是否可信”的问题，所以把后续重点放到了工具边界、SQL 约束、检索版本和前后端展示上。

这不只是增加一个按钮，而是让结果能够带着 SQL、引用和异常信息返回，让调用过程也能检查。遇到失败，系统要告诉使用者是哪一步没完成，而不是只给一段流畅的回答。

我能展示的结果是这些具体模块和本地验证。至于节省了多少人力、影响了多少用户，没有证据就不加。主动性可以体现在主动补齐一个可见问题，不需要夸大成组织级成果。

### Q88｜讲一次失败或没达到预期的经历，你怎么处理？

光储项目里，我尝试过安全强化学习，原本想看能不能在满足约束的同时改善决策效率和成本。但当前比较里，更快的推理没有转化成更好的综合成本。

我没有只挑速度来说明成功，而是固定数据和成本口径继续比较；候选不满足要求时回到 LP-MPC。对于可能原因，我保留进一步实验的方向，没有直接把某个猜测写成结论。

这件事让我更愿意先定评价标准，再看结果。做新方法可以允许实验失败，但真正采用方案时，应该按业务目标做判断，不能因为投入了很多时间就一定要用它。这个案例属于离线实验，不是线上事故。

### Q89｜你和同事意见不一致时，怎样处理？有真实例子吗？

**处理方法可以这样说：**我会先确认争议是目标不同、信息不同，还是实现方式不同。如果都想按时上线，只是一个人想加功能、另一个担心不稳定，就把必须交付的流程、风险和时间成本写清楚，再比较几个方案。

技术争议尽量用小实验或明确标准解决。例如比较两种检索方案，就用同一组问题看召回和耗时；如果涉及业务取舍，再请负责人决定，团队按决定执行。

**真实故事的边界：**现有材料能证明你参加过团队训练营和学生工作，但没有一件完整的同事冲突记录。不要编一个“我说服领导、最后所有人认可”的故事。对方要求真实例子时，选你确实记得的那一次，讲人物职责、分歧、你的动作和实际结果；没有就说明这一段是在讲处理思路。

### Q90｜在学校做项目和去公司实习，最大的区别是什么？

我体会比较明显的是，公司里不能只关注自己这段代码能不能跑。接口会被别人使用，数据有既定口径，修改要能联调、能测试，也要说明对其他模块有什么影响。

比如我在向心力参与接口联调和压力测试，在华为海思做消息编解码与分包相关测试，在中海做光储数据整理和离线验证。这些经历都要求把输入、输出和验证条件说清楚。

学校项目可以让我快速尝试，公司环境则更提醒我考虑协作和结果责任。我现在介绍一个项目，也会主动区分自己做的部分、团队成果和还没有验证的结论。题型参考 S3。

## 移动业务场景与综合面

### Q91｜如果让你给广东移动做一个内部工单系统，怎么设计？

我会先确认谁提单、谁接单、工单经过哪些状态、哪些信息可见，以及超时后如何处理。先把一个最小流程讲清楚：创建、分配、处理、确认、关闭，再扩展转派和撤回等情况。

技术上先考虑简单可维护的模块化服务，核心数据放关系型数据库，附件放对象存储，记录操作历史。状态变化要校验当前状态和操作者权限，避免两个人同时处理把状态覆盖；通知可以异步，但需要处理失败重试和重复发送。

AI 可以辅助分类、总结和推荐知识，不直接替用户做不可逆操作。先从小范围试点开始，衡量处理时长和错误率。这里是方案题，业务流程和技术栈都应以实际要求为准，不说广东移动内部已经这样做。

### Q92｜让你做移动智能客服，怎样落地？

先区分问答和操作。查询公开套餐规则可以用知识库回答；查询用户账单要完成身份和数据权限校验；办理、取消业务等动作还要确认用户意图和具体生效条件，不能仅靠模型一句话执行。

知识库要标明地区、时间、套餐版本和适用客户，避免拿旧活动或其他省份规则答复。回答能给来源，缺信息时继续问，处理不了时转人工，并把已收集的信息一起交过去。

上线前用真实问题与边界样例评测，上线后看解决率、转人工质量、错误办理和投诉，而不只看“机器人回复了多少次”。AI 回复快，但给错资费或乱办理，业务代价可能更大。

### Q93｜你了解哪些运营商业务或术语？云、算力和网络是什么关系？

我理解运营商不只提供手机连接，也有家庭宽带、企业专线、云和物联网等服务。网络负责把用户、设备和数据连接起来；算力负责计算和模型运行；云通常把计算、存储等资源以服务方式提供。业务系统把这些能力组织成用户可使用的服务。

如果问5G，我会先说它是移动通信技术体系，能在不同设计条件下支持更高带宽、低时延和大连接等需求，但这些不是任何场景同时无限满足的保证。

我的优势在系统研发和 AI 应用，通信协议细节会继续补，不冒充无线网络专家。这个岗位的官网重点是软件交付，因此我会把通信背景与系统需求联系起来，而不是把面试变成通信术语背诵。

### Q94｜你用过移动产品吗？有什么技术上的改进建议？

我会选自己确实用过、能说明具体过程的产品，不为了面试临时说“我天天使用”。如果缺少足够使用经验，我会先说明，再把建议表述为假设场景。

例如查询套餐规则，如果用户需要在多个页面找限制条件，我会考虑把套餐、地区、生效时间等条件集中展示，再提供带来源的问答入口。涉及办理时，仍由确定的业务流程校验，模型负责解释和引导。

判断是否有改善，可以看用户完成查询的时间、重复咨询和答错率。我不知道内部架构，就不直接说“你们后端技术太旧”，也不把个人一次网络卡顿当作系统性能结论。S3 中确实出现过产品技术改进追问。

### Q95｜业务人员需求一直变，你怎么办？

先确认是对原需求理解不一致，还是业务真的变化了。对于前一种情况，我会用页面原型、字段示例和验收样例把意思对齐；对于新增变化，说明它会影响哪些接口、数据和交付时间。

我会把当前版本必须完成的部分和可以后续做的部分区分清楚，形成双方都知道的版本范围。小变化可以处理，涉及数据结构或关键流程的大变化需要重新评估。

沟通时不只是说“做不了”，而是给选择：保留原时间就缩范围，必须加功能就调整时间或资源。最终由相关负责人确认取舍，避免各自以为对方已经同意。

### Q96｜领导要求明天上线，但你觉得做不完，怎么办？

我会尽快说明剩余工作和风险，不等到截止时间才说完成不了。先确认明天必须解决的业务目标，再给一个可以验证的最小方案，以及延后完整功能的方案。

如果缺的是非关键展示，可以讨论缩范围；如果缺的是权限、交易一致性或恢复能力，我会明确指出上线后果，不能把已知重大风险藏起来。能并行的任务协调资源，不能并行的部分就据实说明。

确定方案后及时同步进度和阻碍。加班可以解决一部分工作量问题，但不能代替需求澄清，也不能把没有测试过的功能说成已经验证。

### Q97｜你的缺点是什么？别说“太追求完美”。

**适合你、但要符合真实自评的版本：**我有时讲技术会先讲实现细节，前面没有先把问题和结果说清楚。这样对方可能听了很多名词，还不知道我到底做成了什么。

我现在会要求自己先用两三句话说业务问题、个人负责部分和结果，再根据对方的问题展开。比如介绍 Agent，先说“它能查什么、为什么可信、失败怎么处理”，再讲 LangGraph 和向量数据库。

这不是什么包装成优点的缺点，它会影响沟通。我希望通过更早确认对方关心的内容、练习限时表达来改进。

**若不符合你真实情况：**换成你能承认、也能讲清改进动作的不足。别临场编一个长期坚持了半年却没有发生的习惯。

### Q98｜家在哪里？父母做什么？家里支持你来广东吗？

可以先简洁回答：“我目前家在成都，本科在电子科技大学读，硕士在广州。父亲在会计师事务所从事技术管理工作，母亲是医生。”不用主动讲家庭地址、电话等不相关信息。

是否支持去广东要按你真实沟通情况说。若还没正式讨论，可以回答：“我会和家里沟通生活安排，但职业选择主要结合岗位和个人发展考虑。”不能因为家里职业稳定，就推断他们已经同意你去任何城市。

现有资料确认你有亲兄弟姐妹，但没有具体关系、人数和情况，别替自己编成独生子女。家庭题型在 S4、S5 出现过；回答保持自然、适量，再回到求职安排即可。

### Q99｜讲讲你的奖项、学生工作和兴趣。

我参加过字节跳动后端青训营，进阶组总第11名；参加过三创赛，获得省级二等奖；招商银行数字金融训练营中，所在团队获得中西赛区第七组钻石银奖。这些要按证书和材料原名称说明，团队奖不能说成个人全国排名。

我参加过开放原子工作室，负责后端方向的一些工作，包括招新安排和出题；也有院学生会经历，参与组织过学院辩论会等活动。追问某次活动时，要讲自己实际做的部分，不把所有组织工作都说成独立负责。

兴趣包括羽毛球、游泳、绘画和电吉他。选一两个你能聊下去的说就够了，不用硬把每个爱好升华成职场能力。“强网”奖项应使用 Winner Prize 等材料原名，不擅自翻译成冠军。

### Q100｜你项目很多，会不会都是拼框架？到底有多少深度？

这个质疑我能理解。我的项目确实使用了已有框架和基础模型，我不把框架本身当成自己的成果。我希望通过具体实现证明深度，例如 SQL 怎么受约束、数据和知识结果怎样汇合、重复请求怎么处理、失败后怎样恢复。

如果您愿意，我可以选企业 Agent 里只读查询这条链路，从输入、校验、执行预算到异常返回完整讲一遍，也可以解释哪些能力还没有做到。

对我来说，深度不是项目名称很长，而是遇到一个实际问题时，能解释为什么这样做、哪里可能失败，以及怎样验证。我现在的生产经验还有不足，这部分会诚实说明。

### Q101｜问到不会的技术，你怎样回答？

我会先区分是完全没接触，还是知道原理但不记得细节。例如：“这个机制我没有实际使用过。我目前理解它主要解决……，但具体实现我不能凭印象给您一个确定答案。”

如果和做过的东西相关，可以继续说我的分析步骤：“我会先确认它的输入输出、失败方式和与现有系统的关系，再做一个小验证。”如果完全不了解，就直接承认，不绕一大段术语掩盖。

面试中不必把每个问题都硬答成会。能识别自己的知识边界，比一本正经地说错更可取；但已经写在简历上的核心技术，应当能解释到实际实现。

### Q102｜怎么看加班、值班和工作压力？

**按可接受范围表达：**我理解系统开发在上线、故障和关键交付阶段可能需要加班或值班，遇到自己负责的问题，我会积极处理并配合团队安排。

日常我也希望通过合理拆任务、自动化测试和提前暴露风险减少重复返工。长期工作强度、值班安排和补休机制，我希望入职前了解清楚，这样才能做稳定的安排。

不要承诺实际上做不到的“任何时候都可以、长期无休也没问题”。这类问题更重要的是责任心和预期是否一致，而不是回答得越极端越好。

### Q103｜你有什么想问我们的？

我最想了解的是，这个岗位刚入职时会从哪类业务系统或模块开始，团队希望新人前半年先做到什么程度？这样我能更具体地安排入职前的学习。

另外，招聘里写到 AI 编码和 Skill/MCP 建设，我想了解团队现在主要是在试点，还是已有比较成熟的研发流程？新人更多是参与业务开发，还是也会参与这类公共能力建设？

如果还有时间，可以问：“一个功能从开发到上线，团队目前主要经过哪些评审和验证环节？”现场挑一到两条就够，不需要把面试官变成答卷人。流程时间可以最后自然补问，薪资细节更适合 HR 沟通环节。

### Q104｜用英语介绍你的企业 Agent 项目。

I worked on a business analysis agent based on an earlier team prototype. The goal was to help users ask questions about business data and understand the definitions behind the numbers.

I rebuilt the workflow so that data questions use controlled database queries, while knowledge questions use document retrieval. For questions that need both, the system combines the results. I also worked on the web interface and the tool layer.

The most important part for me was making the result easier to check. The system can show the SQL, supporting documents, and warnings. If a query fails or the evidence is missing, it should explain the limitation instead of inventing an answer.

**中文意思：**从团队原型继续重构，分数据和知识两路，展示依据和失败。这段没有虚构生产用户量，也没有声称从零独立完成全部项目。

### Q105｜如果现场突然安排无领导小组讨论，你怎么参与？

我会先读清任务：是排序、资源分配还是提出方案，最后要求交付什么。个人发言先给结论和两三个依据，不急着抢“领导者”。讨论开始后，可以建议先统一评价标准，再讨论不同选项。

有分歧时，我会帮助把观点放到同一套标准下比较；时间不足时提醒剩余任务，推动形成可汇报的结论。别人说得好的地方及时吸收，别人没讲完不随意打断。

没有获得主导角色，也可以贡献信息、澄清条件或做结构化总结。你当前通知没有写群面，本次面经也不能证明该岗位必有群面，这部分是备用准备。

### Q106｜模拟群面：预算有限，先做客户问答、内部研发助手还是智能营销？

我会先提出判断标准：业务价值是否清楚、风险能否控制、数据是否准备好，以及多快能验证。如果题目没有额外条件，我倾向先从范围明确的内部研发或知识辅助试点开始，因为更容易限定用户、人工复核结果和观察效果。

但这不是固定答案。如果材料说明客服重复咨询成本很高、知识库已经完善，而内部研发工具没有合规数据环境，我会把客服问答提前。涉及客户权益和营销触达的功能，要更认真考虑错误、投诉和授权。

我的建议是先保留一个可衡量的小试点，设定阶段目标，再根据实际结果追加预算。最后汇报说明选择标准和未选方案的限制，不能只喊“AI 能带来效率”。

### Q107｜如果互联网公司给你更高薪资，你还会来吗？

薪资当然是重要因素，我不会说完全不在乎。但选择第一份长期工作，我也会看具体岗位、团队培养、业务责任和城市安排。更高的数字如果对应完全不同的工作方向，不能直接比较。

我认真准备广东移动，是因为这个岗位的 AI 辅助研发和系统交付方向适合我。如果双方对职责和发展预期匹配，我会把它作为重要选择。最终我会综合信息后做决定，并在接受录用后履行自己的承诺。

不要在尚未了解方案时作不真实的唯一选择承诺，也不用贬低其他行业来表达意愿。把“我为什么适合这份工作”讲具体，比喊绝对忠诚更自然。

### Q108｜只有30—45秒，你怎么讲清自己的核心优势？

## 技术面补充：基础题与小型代码题

以下 Q111—Q120 是系统开发岗位可能延伸的基础考查，并非查到的同岗原题。先熟悉前面的个人项目；如果时间充足，再用这些题检验基本功。

### Q111｜写 SQL：统计每个地区上个月的成功订单金额，注意什么？

先澄清“上个月”的时区、成功状态，以及金额是否扣退款；不能先写 SQL 再猜口径。下面假设按 `paid_at` 付款时间、`SUCCESS` 状态和订单金额统计，应用已计算好月初边界。它是练习示例，不是移动真实表结构。

```sql
SELECT region_id, SUM(amount) AS total_amount
FROM orders
WHERE status = 'SUCCESS'
  AND paid_at >= :last_month_start
  AND paid_at < :this_month_start
GROUP BY region_id;
```

使用左闭右开的范围，可以避免月底最后一秒或毫秒的边界问题；绑定参数能减少拼接风险。金额通常用精确十进制或最小货币单位表示。用户能看哪些地区，还必须由服务端权限决定。索引要结合实际选择性和执行计划设计，不凭这段 SQL 直接宣布某个索引最优。

### Q112｜写 SQL：查每个部门工资最高的两个人，遇到并列怎么办？

先问“最多两个人”，还是“前两个工资档位的人全部要”。这两个需求不一样。假设用支持窗口函数的数据库，要求最多两个人，可以按工资降序，再用员工 ID 确定同工资的顺序。

```sql
SELECT department_id, employee_id, salary
FROM (
  SELECT department_id, employee_id, salary,
         ROW_NUMBER() OVER (
           PARTITION BY department_id
           ORDER BY salary DESC, employee_id ASC
         ) AS rn
  FROM employees
) ranked
WHERE rn <= 2;
```

如果要求前两个工资档位全部保留，可用 `DENSE_RANK()`，排名表达式只按工资，不要再加入员工 ID 把并列拆开。还要说明空工资是否参与，以及数据库版本是否支持窗口函数。面试官往往在看你有没有先理解“前两名”的含义。

### Q113｜解释二分查找，写一个不容易死循环的版本。

二分查找适用于有序数据。每次看中间位置，根据比较排除一半候选，时间复杂度通常是 O(log n)。关键是区间定义要一直一致，不要一会儿包含右边界、一会儿又不包含。

```python
def binary_search(nums, target):
    left, right = 0, len(nums) - 1
    while left <= right:
        mid = left + (right - left) // 2
        if nums[mid] == target:
            return mid
        if nums[mid] < target:
            left = mid + 1
        else:
            right = mid - 1
    return -1
```

这个版本返回某个匹配位置，不保证是重复元素中的第一个。需要第一个时，找到目标后还要继续收缩左侧搜索范围。练习空数组、只有一个元素、目标不存在和重复元素。S5 的历史面经明确问过二分查找。

### Q114｜给一个字符串，求最长不重复子串长度，怎么想？

用滑动窗口维护一段没有重复字符的区间。右边不断加入字符；一旦新字符上次出现的位置还在窗口内，就把左边移到那个位置之后。左边只能向前，不能被更早的重复位置拉回去。

```python
def longest_unique_length(text):
    last = {}
    left = best = 0
    for right, char in enumerate(text):
        if char in last and last[char] >= left:
            left = last[char] + 1
        last[char] = right
        best = max(best, right - left + 1)
    return best
```

每个字符访问一次，平均时间 O(n)，额外空间与不同字符数量有关。例子 `abba` 的答案是2，不是3；它能检验左边界是否错误后退。这个实现按 Python 字符遍历，不额外处理人眼看到的复杂组合字形。

### Q115｜HashMap 为什么不线程安全？ArrayList 和 LinkedList 怎么选？

HashMap 的普通操作没有提供所有并发读写所需的同步保证，多线程同时修改可能发生丢失更新等问题。需要并发访问时，根据操作语义选择 ConcurrentHashMap 或显式同步；即使用并发容器，“先查没有、再放入”也不自动成为一个原子业务操作，可以考虑合适的原子接口。

ArrayList 基于数组，按下标访问快、内存局部性通常较好；LinkedList 基于链表，已经拿到节点或迭代器的位置时插删方便，但为了找到位置仍可能遍历，而且节点有额外开销。

所以不能一句“经常插入就一定用链表”。要看插入位置是否已知、遍历模式和实际规模。多数常见列表场景，先考虑简单的数据结构，再根据测量决定。

### Q116｜多线程为什么会出错？锁、volatile、线程池各干什么？

多个线程共享可变数据时，一个看似简单的加一，也可能包含读取、计算、写回三步，两个线程交错执行就会丢失更新。锁可以保护需要作为整体处理的临界区，但要控制范围，避免死锁和长时间阻塞。

Java 的 volatile 主要涉及可见性和特定顺序保证，不能把 `count++` 自动变成原子操作。线程池用于复用线程并管理并发，但队列大小、拒绝策略和任务超时同样重要，不能让请求无限堆积。

实际设计先减少共享状态，再选择同步机制。锁住一切虽然容易想，但可能把并发系统变成排队系统；完全不加控制则可能得到错误数据。

### Q117｜进程、线程、堆、栈有什么区别？

进程可以理解为一个具有独立资源和地址空间的运行环境；线程是其中执行任务的单元，同一进程内线程通常共享很多资源。线程之间通信方便，但也更容易互相影响，所以共享数据需要同步。

堆通常存放动态分配、生命周期较灵活的数据；线程的调用栈记录函数调用、局部执行信息等。具体变量放哪里要看语言和运行时，不能绝对说“所有局部变量一定在栈上”。

面试官问“堆和栈”时，也可能是在问数据结构：堆常用于优先队列，栈是后进先出。先确认语境，再解释，避免讲了半天内存而对方其实问的是算法。

### Q118｜TCP 和 UDP 有什么区别？为什么 TCP 要三次握手？

TCP 提供可靠、有序的字节流传输，会处理重传、流量控制和拥塞控制；UDP 提供数据报，不在协议本身保证送达、顺序或重传。选哪个要看应用需要，应用也可以在 UDP 之上实现可靠机制，不能说 UDP 一定“不可靠到不能用”。

TCP 建连时需要双方确认收发能力并同步初始序列号，三次握手是完成这个过程的常见方式。可靠传输不代表业务只执行一次，连接中断时仍可能不知道服务端是否已经处理，所以业务幂等依然必要。

TCP 是字节流，没有天然的业务消息边界，应用要定义长度、分隔符或其他协议来解析。这与你做过的消息编解码、分包实践可以联系起来，但不要把不同协议层混成一个东西。

### Q119｜Transformer、Embedding、LoRA，用简单的话解释。

Transformer 的核心机制之一是注意力，让一个位置的表示能够结合其他相关位置的信息；它不等于数据库查询，也不能保证记忆的事实总是准确。Embedding 是把文本等内容转换成一组数，便于表示和比较，在检索里常用它寻找语义接近的片段。

LoRA 是参数高效微调方法的一类做法，通过训练较少的附加参数来调整模型行为，减少相对于全量微调的训练负担。它不是把新文档直接塞进模型后就能精确查资料的保证。

你简历的强项是应用、检索和评测，不是已完成大规模预训练或 LoRA 训练。会解释这些概念即可；若被问实际训练规模、显卡和训练曲线，没有做过就直接说明。

### Q120｜系统突然变慢但没报错，你会怎样一步步定位？

先确定“慢”是哪些接口、什么时候开始、影响所有用户还是部分用户，并看 p50、p95、吞吐和资源指标。没有错误日志，不代表没有问题，也可能请求都在等待。

顺着 Trace 把耗时分开，看应用排队、连接池、数据库、外部服务、网络和 CPU/I/O。数据库部分再分查询扫描、锁等待和连接；模型调用则区分排队、首个输出和完整生成耗时。最近发布、配置和数据规模变化也要一起看。

找到证据后再做针对性处理，例如减少并发保护下游、取消昂贵查询或回退变更。扩容只有在瓶颈可被扩容缓解时才有用；单条坏 SQL 或全局锁的问题，直接多加应用实例反而可能加重。
